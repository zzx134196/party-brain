## 三、功能模块详细设计

### 3.1 功能一：辅助生成（模板填充）

**目标**：用户输入关键信息，系统自动填充模板生成完整文档。

**实现方案**：

1. **模板管理**
   - 将甲方提供的工作计划、活动策划方案等模板结构化存储
   - 每个模板定义：模板名称、模板类型、必填字段、可选字段、模板正文骨架

2. **交互流程**
   ```
   用户："帮我写一份七一建党节活动策划方案"
     → 意图识别 → 匹配"活动策划方案"模板
     → 提取已有信息(主题: 七一建党节)
     → 追问缺失字段(时间、地点、参与人数、预算等)
     → 用户补充信息
     → LLM 基于模板 + 用户信息生成完整方案
     → 输出文档(支持在线预览 & 导出Word/PDF)
   ```

3. **技术要点**
   - 模板采用 Jinja2/Mustache 格式管理，支持动态字段
   - LLM 使用 few-shot + 模板约束 prompt，确保输出格式统一
   - 支持用户对生成结果进行"再修改"指令（如"把预算部分再详细些"）

**甲方需提供**：各类模板文件（Word格式最佳），明确必填/选填字段

---

### 3.2 功能二：知识问答（党员信息查询 & 统计分析）

**目标**：通过自然语言查询党员信息和进行数据统计分析。

**实现方案**：

1. **数据入库**
   - 将甲方提供的党员信息表单导入结构化数据库(MySQL/PostgreSQL)
   - 标准字段设计：

   | 字段 | 类型 | 说明 |
   |------|------|------|
   | id | INT | 主键 |
   | name | VARCHAR | 姓名 |
   | gender | VARCHAR | 性别 |
   | birth_date | DATE | 出生日期 |
   | join_party_date | DATE | 入党日期 |
   | department | VARCHAR | 所属部门/支部 |
   | position | VARCHAR | 职务 |
   | education | VARCHAR | 学历 |
   | phone | VARCHAR | 联系电话 |
   | status | VARCHAR | 党员状态(正式/预备/转出等) |
   | ... | ... | 根据实际表单扩展 |

2. **查询交互流程**
   ```
   用户："张三是哪个支部的？"
     → 意图识别 → 单条信息查询
     → NL2SQL → SELECT department FROM members WHERE name='张三'
     → 返回结果："张三属于第二党支部"

   用户："统计一下各支部的党员人数"
     → 意图识别 → 统计分析
     → NL2SQL → SELECT department, COUNT(*) FROM members GROUP BY department
     → 返回表格 + 可视化图表
   ```

3. **技术要点**
   - NL2SQL 模块：基于 LLM + 数据库 schema 注入的方式，将自然语言转为SQL
   - 安全兜底：生成的SQL必须经过白名单校验（只允许SELECT，禁止写操作）
   - 统计结果支持表格 + 图表双形态展示
   - 敏感信息脱敏处理（手机号等）

**甲方需提供**：完整的党员信息表单(Excel/CSV)，明确字段含义

### 3.3 功能三：政策规则库 + 合规判断

**目标**：构建政策知识库，用户提问时系统检索相关条款并判断是否满足要求。

**实现方案**：

1. **知识库构建**
   - 文档解析：将政策PDF/Word文件解析为结构化文本
   - 文档切片：按章节/条款级别切片，保留层级关系
   - 向量化：使用 Embedding 模型将切片向量化
   - 存储：向量数据库(Milvus/FAISS) + 原文存储

2. **查询与判断流程**
   ```
   用户："发展党员需要满足什么条件？"
     → 意图识别 → 政策查询
     → 向量检索 → 召回相关条款(Top-K)
     → LLM 整合条款内容给出回答
     → 附带原文引用出处

   用户："李四今年22岁，入党积极分子培养满1年，能否发展为预备党员？"
     → 意图识别 → 合规判断
     → 向量检索 → 召回发展预备党员相关条款
     → LLM 逐条对照判断
     → 输出判断结果 + 依据条款 + 不满足项提示
   ```

3. **技术要点**
   - RAG 检索精度优化：混合检索(向量+关键词)、Rerank 重排序
   - 判断结果必须附带条款原文引用，做到有据可查
   - 设置置信度阈值，低于阈值时提示"建议人工复核"
   - 支持政策文件的增量更新（新增/替换/废止）

**甲方需提供**：全部政策规则文件（PDF/Word），标注有效性状态

### 3.4 功能四：文件内容差异提取（待需求确认）

**目标**：提取不同文件之间的内容差异项。

**预设方案**（待甲方确认后调整）：

1. **场景A：两份同类文件的差异对比**
   - 上传两份文件 → 解析文本 → 结构化对齐 → 差异标注
   - 输出差异报告（新增项 / 删除项 / 修改项）

2. **场景B：多版本政策的变更追踪**
   - 新旧版政策上传 → 条款级对比 → 输出变更清单
   - 标注：新增条款 / 废止条款 / 修改条款（含修改前后对照）

3. **场景C：从文档中提取特定字段差异**
   - 定义提取模板 → 批量解析文件 → 结构化对比 → 输出差异表

**⚠️ 需与甲方确认**：具体使用场景、输入文件类型、期望输出格式

## 四、技术选型建议

| 组件 | 推荐方案 | 备选方案 |
|------|---------|---------|
| 大语言模型 | 私有化部署(Qwen2.5/GLM4/DeepSeek) | API调用(通义千问/智谱API) |
| Embedding模型 | bge-large-zh-v1.5 | m3e-large |
| 向量数据库 | Milvus | FAISS / Chroma |
| 结构化数据库 | MySQL 8.0 | PostgreSQL |
| 文档解析 | PDF: PyMuPDF; Word: python-docx | Unstructured.io |
| 后端框架 | Python FastAPI | Flask |
| 前端框架 | React + Ant Design | Vue3 + Element Plus |
| 对话框架 | LangChain / LlamaIndex | 自研 Agent 框架 |

> **注**：如单位有数据安全要求（涉及党员个人信息），强烈建议**私有化部署LLM**，不走外部API。

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 政策判断准确率不足 | 可能给出错误指引 | 设置置信度阈值 + 人工复核提示 |
| 党员数据质量差 | 查询结果不准确 | 入库前数据清洗 + 校验规则 |
| 模板覆盖不全 | 无法满足所有场景 | 预留通用模板 + 支持后续添加 |
| 功能四需求不明确 | 开发方向偏差 | 优先确认需求再开发 |
| 数据安全合规 | 党员信息泄露风险 | 私有化部署 + 权限管控 + 日志审计 |
